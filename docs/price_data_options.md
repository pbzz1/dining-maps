# 가격 데이터 확보 방안 조사

공식 브랜드 사이트에서 가격을 거의 얻을 수 없다는 결론(`docs/brand_survey.md`) 이후, 다른 경로를
조사한 결과.

## 출발점: 공식 채널의 한계

46개 브랜드를 조사한 결과 **영양정보와 가격을 함께 제공하는 곳은 버거킹·배스킨라빈스 2곳뿐**이다.
2곳으로는 슈링크플레이션 탐지나 외식물가지수 대조가 성립하지 않는다.

프랜차이즈가 가격을 공시하지 않는 데는 구조적 이유가 있어 보인다 — 일반매장과 특수매장(공항·
휴게소·터미널)의 가격이 다르고 배달가와 매장가도 달라서, 단일 가격을 공시하기 어렵다. 실제로
한솥도시락은 가격을 표기하면서 "메뉴에 표기된 가격은 **권장가격**입니다"라고 명시하고 있다.

---

## 1. 카카오맵 플레이스 메뉴 정보 — ❌ 확인 결과 불가

우리는 이미 4,063개 매장의 `kakao_place_id`를 갖고 있으니, 카카오 API로 매장별 메뉴·가격을
가져올 수 있다면 가장 자연스러운 경로였다. **직접 확인해본 결과 불가능하다.**

카카오 로컬 API 키워드 검색 응답의 전체 필드는 다음과 같고, 메뉴나 가격 관련 필드가 없다:

```
address_name, category_group_code, category_group_name, category_name,
distance, id, phone, place_name, place_url, road_address_name, x, y
```

`place_url`로 연결되는 카카오맵 웹페이지에는 매장이 등록한 메뉴·가격이 표시되는 경우가 있지만,
그건 **API가 아니라 웹페이지를 긁는 것**이라 별개 문제다(등록률도 매장마다 들쭉날쭉하다).

---

## 2. 한국소비자원 참가격 — ⭕ 가장 현실적인 공공데이터

정부가 운영하는 가격정보 포털(`price.go.kr`)에서 **외식비 가격정보**를 제공하고, 공공데이터포털에
API도 등록되어 있다.

- 외식비 가격정보: <https://www.price.go.kr/tprice/portal/servicepriceinfo/dineoutprice/dineOutPriceList.do>
- 공공데이터포털 API: <https://www.data.go.kr/data/3043385/openapi.do>

**장점**
- 공공데이터라 라이선스·크롤링 정책 문제가 없다
- 지역별 가격을 제공하므로 우리 지도 서비스의 위치 축과 결합할 수 있다
- 정기 조사라 시계열이 쌓인다 → 스케줄링에 명확한 이유가 생긴다

**한계 (중요)**
조사 품목이 **김밥·자장면·삼겹살 같은 일반 외식 품목**이지 "빅맥", "와퍼" 같은 프랜차이즈 개별
메뉴가 아니다. 즉 **우리 메뉴 데이터와 1:1로 매칭되지 않는다.**

그래서 "빅맥 가격이 올랐나"는 답할 수 없고, **"우리가 다루는 지역의 외식물가가 어떻게 움직이나"**
라는 배경 지표로만 쓸 수 있다. 지도에 "이 지역 평균 외식비" 같은 맥락을 얹는 용도.

---

## 3. 뉴스 기사에서 가격 인상 추출 — △ 실험적이지만 DE 관점에서 흥미로움

프랜차이즈 가격 인상은 반드시 기사화되고, 기사에는 구체적 금액이 들어간다
("빅맥 세트를 7,200원에서 7,500원으로 인상").

**장점**
- 비정형 텍스트 → 정형 데이터 추출은 데이터 엔지니어링에서 다루는 전형적 문제다
- LLM으로 추출 파이프라인을 만들면 포트폴리오 소재로 강하다
- 네이버 뉴스 검색 API 등 공식 API 사용 가능

**한계**
- 인상된 메뉴만 잡힌다. 안 오른 메뉴의 현재 가격은 알 수 없다 → **가격 테이블을 채우는 게 아니라
  "변동 이벤트"만 수집**하는 셈
- 기사 표현이 제각각이라 추출 정확도 검증이 필요하다
- 초기 기준가격이 없으면 변동만으론 절대 가격을 복원할 수 없다

버거킹·배스킨라빈스의 실측 가격을 기준선으로 삼고 뉴스에서 변동을 붙이는 조합은 가능하지만,
2개 브랜드로는 여전히 표본이 부족하다.

---

## 4. 통계청 KOSIS 외식물가지수 — ⭕ 보조 지표로는 확실

월 단위로 확실히 갱신되고 API도 제공된다. 다만 **지수**라서 개별 메뉴 가격이 아니다.
2번(참가격)과 성격이 비슷하며, "공식 물가지수 vs 실제 관측 가격" 대조용으로만 의미가 있다.
버거킹·배스킨라빈스 2곳의 실측치와 대조하는 정도는 가능하지만 분석이라 부르기엔 표본이 빈약하다.

---

## 5. 배달앱 (배민·요기요·쿠팡이츠) — ❌ 권장하지 않음

가격 데이터 자체는 가장 풍부하지만:

- **이용약관상 크롤링이 금지**되어 있는 경우가 많다. 포트폴리오에 올릴 프로젝트에서 ToS를 어기는
  건 그 자체로 감점 요인이다
- 배달가는 매장가보다 비싸고 플랫폼마다 달라서, "이 브랜드의 가격"이라고 말하기 어렵다
- 로그인·봇 차단이 걸려 있어 기술적으로도 불안정하다

같은 이유로 **브랜드 주문 앱 API 리버스 엔지니어링**(맥딜리버리, 사이렌오더 등)도 권장하지 않는다.

---

## 결론 및 제안

**가격을 메뉴 단위로 채우는 건 현재 조건에서 사실상 불가능하다.** 공식 채널엔 없고, 공공데이터는
품목 단위이고, 배달앱은 약관 문제가 있다.

따라서 원래 구상했던 슈링크플레이션 탐지는 **접는 것이 맞다.** 데이터가 뒷받침되지 않는 기능을
억지로 넣으면 "가격 2개 브랜드만 있는데 물가 분석을 한다"는 약점이 그대로 드러난다.

대신 현실적인 선택지는 두 가지다.

1. **가격을 부가 정보로만 취급** — 버거킹·배스킨라빈스처럼 가격이 있는 브랜드는 화면에 표시하고
   ("1,000원당 단백질" 지표도 이 두 곳에 한해 계산 가능), 나머지는 비워둔다. 이미 스키마에
   `price_krw` 컬럼이 nullable로 있어서 추가 작업이 거의 없다.

2. **가격은 접고 매장 개폐업 추세로 간다** — 이미 `last_seen_at` 인프라가 있고, 4,000개 매장은
   실제로 매주 변한다. "시간에 따라 변하는 데이터"라는 원래 목적에는 이쪽이 더 부합한다.

두 방향은 배타적이지 않으므로 1번(비용 거의 0)을 해두고 2번을 본 축으로 가는 걸 추천한다.

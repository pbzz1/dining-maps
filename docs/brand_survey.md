# 브랜드 확장 조사 대장

어떤 프랜차이즈가 영양정보·가격을 공개하는지 조사한 결과와, 그 조사를 반복 가능하게 만든 방법.

- 대장 파일: `data/brand_survey.csv`
- 갱신 스크립트: `scripts/survey/survey_brands.py`

## 왜 대장을 따로 만들었나

브랜드를 늘리려면 "이 브랜드가 영양정보를 공개하는가"부터 확인해야 하는데, 이걸 매번 즉흥적으로
조사하면 **같은 브랜드를 두 번 조사하거나, 왜 탈락시켰는지 잊어버린다.** 실제로 조사해보니
탈락 사유가 브랜드마다 제각각이었다(영양정보 자체가 없음 / 이미지로만 공개 / 팝업이 빈 페이지 /
도메인 접근 불가 등). 이 판단 근거를 남겨두지 않으면 나중에 재검토가 불가능하다.

그래서 조사 결과를 CSV 대장으로 관리하고, 새 브랜드를 추가할 때마다 스크립트를 다시 돌려
갱신하는 구조로 만들었다.

## 사용법

새 브랜드를 조사 대상에 넣으려면 `scripts/survey/survey_brands.py`의 `PROBE_TARGETS`에 추가한다:

```python
PROBE_TARGETS = {
    "브랜드명": ("카테고리", ["후보 URL 1", "후보 URL 2", ...]),
}
```

그리고 실행하면 `data/brand_survey.csv`가 통째로 갱신된다.

```bash
python scripts/survey/survey_brands.py
```

### 대장의 빈칸을 채우는 두 경로

대장에는 두 종류의 빈칸이 있고, 채우는 방법이 다르다.

**1. `viable`인데 `data/*.csv`가 없는 브랜드 (10곳)** — 영양정보가 있는 건 확인됐으니
크롤러만 쓰면 된다.

```bash
python scripts/crawl/crawl_viable_brands.py --list          # 브랜드와 신뢰도 확인
python scripts/crawl/crawl_viable_brands.py --brand bhc     # 하나씩
python scripts/crawl/crawl_viable_brands.py                 # 전체
```

파서는 두 등급으로 나뉜다. `VERIFIED`(버거킹·스타벅스·이디야·BHC·포케올데이)는 조사
당시 브라우저로 구조를 본 브랜드라 구조를 특정해 파싱한다. `UNVERIFIED`(배스킨라빈스·
빽다방·커피빈·할리스·도미노피자)는 **키워드 프로브만 통과했고 마크업은 본 적이 없어서**
`crawl_common`의 범용 테이블/텍스트 추출에 의존한다. 0행이 나오거나 컬럼이 비면 파서를
고쳐야 한다는 뜻이고, 그때는 구조부터 본다.

```bash
python scripts/survey/inspect_page.py https://www.hollys.co.kr/menu/espresso.do
```

이 스크립트는 HTML을 통째로 뱉지 않고 **테이블 개수·헤더·매핑 결과·영양 텍스트를 담은
클래스명**만 20줄 정도로 요약한다. 파서를 쓰는 데 필요한 건 그게 전부인데 원본 HTML은
100KB씩 되기 때문이다.

**2. `unknown`이라 `nutrients` 칸이 아예 빈 브랜드 (26곳)** — 실패 사유를 보면 대부분
"영양정보가 없다"가 아니라 **1차 프로브의 fetch가 실패했을 뿐**이다.

```bash
python scripts/survey/resurvey_unknown.py --dry-run    # CSV 안 건드리고 결과만
python scripts/survey/resurvey_unknown.py              # 대장 갱신
```

1차 프로브가 고정해 뒀던 축(UA·스킴·호스트·경로)을 전부 흔들어 다시 시도한다. 순회는
**경로 우선**이다 — 실패 원인 다수가 www/비www 같은 호스트 철자 문제라, 이미 실패한
호스트에 경로만 20개 시도하면 요청 예산을 헛되이 쓴다. 모바일 UA는 데스크톱이 실패했거나
영양 키워드가 0종일 때만 추가로 시도한다.

`survey_brands.py`가 CSV를 통째로 다시 쓰는 것과 달리 이쪽은 **해당 행만 제자리에서
수정**하므로, 손으로 확인한 adopted/viable/rejected 행은 건드리지 않는다. `surveyed_at`도
뭔가 새로 알아낸 행만 갱신한다 — 그래야 이 컬럼이 "스크립트를 마지막으로 돌린 날"이 아니라
"마지막으로 뭔가 알아낸 날"이라는 뜻을 유지한다.

JS 렌더링으로 판정된 브랜드(설빙·뚜레쥬르·파리바게뜨·신전떡볶이·미스터피자·피자헛·KFC)는
재시도로 해결되지 않는다. urllib이 아니라 브라우저 도구가 필요하다는 뜻이고, 대장에도
`js_rendered`로 남겨 재시도 대상에서 구분한다.

## 자동 프로브 + 수동 확인의 병합

스크립트는 두 종류의 정보를 합쳐서 CSV를 만든다.

**자동 프로브** — 후보 URL을 순서대로 가져와서 HTML에 영양 키워드(열량/kcal/나트륨/단백질/당류/
포화지방 등)가 몇 종 있는지 센다. 4종 이상이면 `viable`, 1~3종이면 `partial`, 0종이면 `unknown`.

**수동 확인(`MANUAL_FINDINGS`)** — 자동 프로브로는 판정할 수 없는 브랜드를 브라우저로 직접 확인한
결과. **자동 프로브 결과를 덮어쓴다.**

수동 확인이 필요한 이유는 명확하다. 버거킹·KFC·교촌 같은 사이트는 JS로 렌더링해서 HTML만 받아보면
영양 키워드가 하나도 안 나온다. 실제로 버거킹은 자동 프로브로는 "영양정보 없음"으로 보이지만,
브라우저로 확인하니 `BKR0634.json` API에 영양정보와 가격이 모두 있었다. 자동 프로브만 믿으면
이런 브랜드를 잘못 탈락시킨다.

CSV의 `notes` 컬럼에 `[수동확인]` 접두사가 붙은 행이 브라우저로 검증한 것이다.

## status 값의 의미

| status | 뜻 |
|---|---|
| `adopted` | 이미 파이프라인에 포함되어 크롤링 중 |
| `viable` | 영양정보 확보 가능. 크롤러만 만들면 됨 |
| `rejected` | 공식 채널에 영양정보가 없어서 불가 |
| `unknown` | 판정 보류 — 접근 실패했거나 JS 렌더링이라 브라우저 확인 필요 |

`unknown`은 "영양정보가 없다"가 아니라 **"아직 확인 못 했다"**는 뜻이다. 이 구분이 중요한 이유는,
`rejected`는 재조사할 필요가 없지만 `unknown`은 재조사하면 살아날 수 있기 때문이다.

## nutrition_format 값의 의미

`status`가 "쓸 수 있나"라면 `nutrition_format`은 **"못 쓴다면 왜, 그래서 다음에 뭘 해야 하나"**다.
1차 조사 때는 실패를 전부 `unreachable`로 뭉갰는데, 그러면 후속 작업을 계획할 수 없어서
실패 사유별로 쪼갰다. 사유마다 필요한 일이 완전히 다르기 때문이다.

| format | 뜻 | 다음 할 일 |
|---|---|---|
| `server_html` / `json_api` | 크롤링 가능 | 파서 작성 |
| `image` | 영양정보가 이미지로만 공개 | 수동 전사 |
| `js_rendered` | 페이지는 받았으나 텍스트가 5% 미만인 SPA 껍데기 | `find_spa_api.py`로 배후 API 발굴 |
| `dns_failure` | 도메인이 DNS에 없음 | 정확한 도메인 재확인 (수 분) |
| `blocked` | 메뉴 경로가 403/406 (WAF 차단) | 브라우저 도구 필요 |
| `path_unknown` | 홈페이지만 도달, 메뉴 페이지 미확인 | 메뉴 경로 재확인 |
| `none` | 메뉴 페이지까지 확인했으나 영양정보 없음 | 없음 (rejected) |

`js_rendered` 판정은 추측이 아니라 **텍스트/HTML 비율 측정**이다. 손으로 확인한 SPA들이
0.8~3%대(BBQ는 77KB 중 텍스트 650자, 컴포즈커피는 6.5KB 중 57자)인 반면 서버 렌더링
메뉴 페이지는 자릿수가 다르다. 5%면 여유 있게 갈린다.

### 대장을 덮어쓰지 않기 위한 두 가지 규칙

재조사 스크립트가 자동 판정으로 기존 정보를 **지워버리는** 사고가 실제로 났고, 그래서
`resurvey_unknown.py`에 가드를 넣었다.

- **`[수동확인]` 노트는 지우지 않고 뒤에 붙인다.** 사람이 페이지를 열어보고 적은 내용은
  키워드 프로브가 재발견할 수 없다. 교촌치킨·BHC의 `100g당 표기`가 그 예다. 등급 자체는
  영향받지 않는다(diet_score는 영양소를 열량으로 나눈 밀도라 일정 배율은 상쇄된다) — 하지만
  잃으면 화면에 표시하거나 다른 브랜드와 비교할 때 100g값과 1회 제공량값을 같은 숫자처럼
  보여주게 되어 사용자가 잘못 읽는다. 그래서 `crawl_common.STANDARD_COLUMNS`에
  `nutrition_basis` 컬럼을 두어 행마다 기준을 남긴다.
- **구체적인 URL을 루트로 덮어쓰지 않는다.** 홈페이지밖에 못 갔다고 기록된 경로를 `/`로
  바꾸면, 한 호스트를 공유하는 본죽·본죽&비빔밥·본도시락처럼 브랜드 구분 자체가 사라진다.
  쿼리 템플릿(`?product_id=`)도 같은 이유로 보존한다 — 상품을 순회하는 방법을 담고 있어서
  파서를 쓸 사람에게는 그게 URL의 전부다.

### 조사 기록과 실제가 달랐던 사례

실사(파서 작성)를 하고 나서야 드러난 것들이다 — 조사 단계의 키워드 프로브는 "영양 단어가
페이지에 보이는가"만 셀 뿐 그 값이 실제로 채워지는지는 확인하지 않기 때문에 이런 오차가 생겼다.

- **BHC·포케올데이**: 기록된 URL에 real data가 없었다. BHC는 표가 `-`로 채워진 빈 템플릿이고
  React가 API로 채우는 구조, 포케올데이는 1일 영양성분 기준치(2000kcal) 1행을 상품 데이터로
  착각한 것이었다.
- **버거킹**: 기록된 API(BKR0632/BKR0634)엔 가격과 열량만 있고 나머지 영양정보가 없었다.
  실제 영양정보는 기록에 없던 `BKR0347` 엔드포인트가 전체 상품을 한 번에 반환한다. 게다가
  이 사이트는 WAF가 urllib/curl을 TLS 단계에서 차단해 브라우저 세션 안에서 직접 fetch를
  실행해야 했다.
- **교촌치킨**: 기록된 nutrients("당류,포화지방")가 API에 아예 없는 필드였다. 실제 필드는
  CALORIE/PROTEIN/CARBOHYDRATE/FAT/NATRIUM뿐이라, 이 브랜드는 diet_score의 필수 영양소
  (당류·포화지방)가 부족해 채점 대상에서 자동 제외된다.

이 오차들의 공통점은 전부 **"페이지가 뭔가를 보여준다"를 "실제 데이터가 있다"로 착각**한
경우라는 것이다. 자동 프로브는 이 둘을 구분하지 못하므로, viable 판정은 파서를 실제로 돌려
행이 나오는 것을 볼 때까지는 잠정적이라고 봐야 한다.

### 재조사 필요 25곳

대부분 두 가지 사유다.

1. **JS 렌더링** (피자헛·파리바게뜨·미스터피자·설빙 등 17곳) — HTML만으론 판정 불가. 브라우저 확인 필요
2. **접근 실패** (죠스떡볶이·푸라닭·폴바셋 DNS 실패, 쉐이크쉑·슬로우캘리 경로 미확인 등) — URL을 못 찾았거나 도메인 응답 없음

특히 **KFC는 가격이 확인된 브랜드**라 우선순위가 높다. 주문 페이지에 가격이 표시되고
("복버켓 16,400") "영양정보표 및 원산지 정보" 링크도 있는데, 그 링크 내용을 아직 확인하지 못했다.

#### JS 렌더링 17곳 — 배후 API 탐색 결과 (2026-08-12)

`scripts/survey/find_spa_api.py`로 각 사이트의 JS 번들을 정적 스캔해 배후 API를 찾아본 결과다.

| 결과 | 브랜드 | 다음 단계 |
|---|---|---|
| API 발견, 스코프 문제 | **BBQ** | `/api/delivery/menu/category` 등 확인. 배달 매장(store) 단위로 스코프돼 있어 매장 id 없이는 빈 배열. 매장 선택 흐름까지 재현 필요 |
| API 흔적 전혀 없음 (13곳) | 설빙·KFC·신전떡볶이·네네치킨·노랑통닭·처갓집양념치킨·컴포즈커피·미스터피자·본도시락·본죽·본죽&비빔밥 등 | Next.js 서버사이드 렌더링(SSR)으로 추정 — 데이터를 서버에서 미리 그려 보내기 때문에 클라이언트 JS 번들에 fetch 경로가 아예 안 남는다. 브라우저 네트워크 탭으로 직접 열어봐야 함 |
| 무관한 API만 발견 | 파리바게뜨(카카오톡 공유 SDK), 피자헛(`/api/csm/csp` 등 프레임워크 공통 헬퍼) | 위와 동일 |
| 창업 포털이라 메뉴 자체가 없음 | 프랭크버거 | `frankburger.co.kr`은 가맹 안내 사이트고 실제 메뉴 사이트는 별도 도메인으로 추정. 재조사 필요 |
| 홈페이지 접근 자체 실패 | 타코벨 | 연결 거부(WinError 10061) — 서비스 중단이거나 도메인이 바뀌었을 가능성 |

정적 스캔이 API를 못 찾았다고 해서 API가 없다는 뜻은 아니다 — SSR 사이트는 애초에
클라이언트 쪽에 fetch 코드가 없을 수 있다. 이런 곳은 다음 단계가 정적 스캔의 반복이
아니라 **브라우저를 열어 실제 네트워크 탭을 보는 것**이다 (BBQ·버거킹·교촌치킨·BHC·
스타벅스가 전부 이 방법으로 뚫렸다).

## SSL 검증 우회에 대해

국내 프랜차이즈 사이트 중 인증서 체인이 불완전한 곳이 많아서, 검증 실패 시 한 번 더 검증 없이
시도하도록 했다. 이 우회로 커피빈 등이 회복됐다.

조사용 스크립트에 한정한 판단이다 — 공개 페이지를 읽기만 하고, 여기서 얻은 데이터를 신뢰 경계
안으로 들이지 않는다. **실제 크롤러를 만들 때는 브랜드별로 인증서 문제를 따로 확인해야 한다.**

## 가격 데이터에 대한 결론

당초 가격 기반 기능(슈링크플레이션 탐지, 외식물가지수 대조)을 검토했다. 조사 단계에서는
**가격과 영양정보를 함께 제공하는 브랜드가 버거킹·배스킨라빈스 2곳뿐**이라고 판단했으나,
실사 과정에서 BHC·도미노피자도 가격을 함께 제공한다는 게 드러나 **4곳**으로 늘었다
(배스킨라빈스는 실제로는 가격이 없었다 — 조사 기록이 틀렸던 항목 중 하나).

- 맥도날드: 영양 API에 `price` 필드가 있으나 179개 전부 `null`이고, 공식 메뉴 페이지에도 가격 표기가 없다
- 스타벅스·이디야·빽다방·커피빈·할리스·포케올데이: 영양정보만 있고 가격 없음
- 굽네치킨·한솥도시락: 가격은 있으나 영양정보가 없어 대상이 아님
- KFC: 가격은 확인됐으나 영양정보 판정 보류 (JS 렌더링, 재조사 필요)

프랜차이즈가 가격을 공시하지 않는 건 구조적 이유로 보인다 — 일반매장과 특수매장(공항·휴게소·
터미널)의 가격이 다르고, 배달가와 매장가도 다르기 때문에 단일 가격을 공시하기 어렵다.

**4곳으로도 슈링크플레이션 분석이나 물가지수 대조가 안정적으로 성립한다고 보긴 어렵다.**
공식 채널 외의 경로는 `docs/price_data_options.md` 참고.

# 데이터 품질 검증 + 변화 감지

`scripts/pipeline/snapshot_and_validate.py`가 하는 일과, 왜 이게 필요한지.

## 왜 만들었나

기존 파이프라인에는 두 가지 구멍이 있었다.

**1) 크롤러가 조용히 깨진다.** `load_data.py`는 UPSERT라서, 브랜드가 사이트를 개편해서 파서가
엉뚱한 값을 뱉기 시작하면 그게 그대로 서빙 테이블을 덮어쓴다. 에러도 안 나고 태스크도 "성공"으로
끝난다. 실제로 이 프로젝트에서 세 번 겪었다:

- 롯데리아 파서에서 빈 셀을 걸러내다가 컬럼이 한 칸씩 밀려서, 원산지 텍스트가 카페인 컬럼으로 들어갔다
- 아메리카노류가 전부 A등급으로 나왔다 (100kcal 미만 메뉴에서 밀도 계산이 왜곡)
- 도미노피자 열량 중앙값이 1,905kcal로 다른 브랜드(120~614)의 3~15배였다. 파서가 **피자 한 판
  전체(총중량)** 컬럼을 읽고 있었고(L 사이즈 1,248g / 3,515kcal), 같은 표에 있는 1회분(150g)
  컬럼을 놓쳤다. 덤으로 "사이드"로 적재되던 9/10/11번 표는 사이드디시가 아니라 **도우·소스·치즈
  성분 분해표**였다 — 피자 행과 중복 계상되던 데이터다 (`더블 치즈 엣지L 2,535kcal`)

셋 다 **사람이 눈으로 발견**했지, 자동으로 잡힌 게 아니다. 매달 자동 실행되는 파이프라인에서
이런 일이 나면 아무도 모르는 채로 나쁜 데이터가 서비스에 나간다.

**2) 이력이 없다.** UPSERT는 이전 값을 지운다. 그래서 다시 크롤링해도 "빅맥 나트륨이 작년보다
늘었나", "이 메뉴가 언제 단종됐나" 같은 걸 알 수 없다. 재크롤링에 남는 게 없으니 스케줄링 자체가
의미를 잃는 구조였다.

## 어떻게 해결했나

파이프라인에 크롤링과 적재 **사이**에 게이트를 하나 넣었다.

```
crawl_* (4개 병렬)  →  snapshot_and_validate  →  load_data  →  compute_diet_score
                            (실패 시 여기서 멈춤 ─ 아래는 실행 안 됨)
```

게이트가 실패하면 `load_data`가 아예 안 돌기 때문에, **이미 서빙 테이블에 있는 정상 데이터가
살아남는다.** 이게 핵심이다.

## 저장 구조 (append-only)

`menu_item` / `nutrition_fact`는 "지금 이 순간의 값"만 갖는 서빙용 테이블로 그대로 두고,
이력은 별도의 append-only 테이블에 쌓는다.

| 테이블 | 내용 |
|---|---|
| `crawl_run` | 크롤링 실행 1건 (시각, 출처, passed/failed) |
| `menu_snapshot` | 그 실행이 본 메뉴 항목 (run별 스냅샷, 절대 UPDATE 안 함) |
| `nutrition_snapshot` | 그 실행이 본 영양성분 (`nutrition_fact`와 같은 key-value 모양) |
| `data_quality_check` | 검증 룰별 결과 (pass/warn/fail) |
| `menu_change_log` | 이전 실행 대비 diff + 판정 |

**실패한 run도 스냅샷은 남긴다.** "그때 크롤러가 뭘 봤는지"가 나중에 원인 분석에 필요하기 때문.
대신 다음 실행은 **마지막으로 passed한 run**과 비교한다 — 깨진 데이터를 기준선으로 삼으면
그다음 정상 데이터가 전부 "변경됨"으로 잡히기 때문이다.

## 검증 룰

| 룰 | 판정 | 기준 |
|---|---|---|
| `brand_has_rows` | **fail** | 이전엔 있던 브랜드가 이번엔 0건 |
| `row_count_stability` | **fail** | 브랜드 항목 수가 이전 대비 50% 초과 감소 |
| | warn | 20% 초과 감소 |
| `value_range` | **fail** | 물리적으로 불가능한 값 (칼로리 5000 초과, 단백질 300g 초과, 음수 등) |
| `nutrient_coverage` | **fail** | 이전에 80% 이상 항목에 있던 영양소가 이번엔 50% 미만에만 존재 |

`value_range`의 상한은 "실제 제품이면 절대 나올 수 없는" 선으로 잡았다. 파싱이 밀려서 나트륨(mg)
값이 단백질(g) 칸에 들어가면 수백~수천이 되는데, 진짜 단백질 300g짜리 메뉴는 없기 때문에 이 선에서
걸린다.

`nutrient_coverage`는 컬럼이 통째로 밀리는 경우를 노린다. 밀린 칸에는 숫자가 아닌 텍스트가 들어가고,
파싱하면 그냥 없는 값이 되므로 커버리지가 급락한다.

## 변화 판정: "파서 버그" vs "실제 메뉴 변경"

이게 이 시스템의 핵심 아이디어다. 값이 바뀐 걸 감지하는 건 쉽지만, **그게 브랜드가 진짜 레시피를
바꾼 건지 우리 크롤러가 깨진 건지 구분하는 게 어렵다.**

사용한 신호: **한 브랜드의 항목 중 30% 초과가 동시에 같은 필드에서 움직이면 구조적 문제로 본다.**

근거는 단순하다. 브랜드는 메뉴를 한 번에 몇 개씩 리뉴얼하지, 하룻밤 사이에 전 메뉴의 나트륨을
동시에 바꾸지 않는다. 반대로 파서가 깨지면 그 브랜드의 **모든** 항목이 같은 방식으로 틀어진다.

- 30% 초과가 같은 필드 이동 → `suspected_parser_bug`
- 그 외 → `real_change`

항목이 5개 미만인 브랜드에는 이 룰을 적용하지 않는다 (2개 중 1개만 바뀌어도 50%가 되어버려서
의미가 없다).

## 실제로 테스트했다

의도적으로 롯데리아 CSV에서 단백질↔나트륨 컬럼을 뒤바꿔서 (예전에 실제로 겪은 컬럼 밀림 버그와
같은 유형) 게이트에 넣어봤다:

```
run #3: snapshotted 314 menu items (comparing against run #2)
quality checks: fail=57, pass=5
  [value_range] 롯데리아: 리아 두툼새우: protein=1300.0 outside [0, 300]
  ... (57건)
changes: 188 (0 real_change, 188 suspected_parser_bug)

FAILED quality gate -- not safe to load into the serving tables.
EXIT CODE: 1
```

- `value_range`가 나트륨 값이 단백질 칸에 들어간 걸 57건 잡아냈다
- 변경 188건이 **전부** `suspected_parser_bug`로 분류됐다 (`real_change` 0건) — 구조적 변화
  판정이 의도대로 작동
- exit code 1 → Airflow에서 `load_data`가 스킵되어 서빙 테이블 보호

이후 정상 데이터로 복구하고 다시 실행하니, 실패한 run #3을 건너뛰고 마지막 정상 run #2와
비교해서 변경 0건으로 통과했다.

## 알려진 한계

- **판정 임계값(30%, 50% 등)은 경험적 추정치다.** 실제 운영 데이터가 쌓이면 재조정이 필요하다.
  특히 메뉴 수가 적은 브랜드(서브웨이 25개, 맘스터치 34개)에서는 몇 건만 바뀌어도 비율이 크게 튄다.
- **진짜 대규모 리뉴얼은 오탐이 난다.** 브랜드가 정말로 전 메뉴를 개편하면 `suspected_parser_bug`로
  잡힌다. 지금은 자동 차단이 아니라 "판정을 기록"만 하므로 사람이 보고 판단하면 되지만,
  자동화 수준을 높이려면 이 부분을 다뤄야 한다.
- **이력이 아직 얕다.** 스냅샷을 이제 막 쌓기 시작했으므로 "1년간 나트륨 추이" 같은 분석은
  시간이 지나야 가능하다.
- 맘스터치는 자동 크롤링 대상이 아니라서 (이미지로만 공개) 스냅샷은 남지만 매번 같은 값이다.
- `menu_item`은 UPSERT만 하고 DELETE는 하지 않는다. 단종된 메뉴가 서빙 테이블에 남아있을 수
  있다 — `menu_change_log`의 `removed` 기록으로 확인은 가능하지만, 정리 로직은 아직 없다.
